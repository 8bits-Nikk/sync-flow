# Sync Flow wire protocol, version 1

Status: **Draft for 0.x** (M0-12). Normative. Source: PLAN.md §5 and DECISIONS.md D-08 to D-15.
Machine-readable companion: [openapi.yaml](openapi.yaml). Conformance: `npx sync-flow test` (M2-14) checks
every **MUST** in this document.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119.

## 1. Overview

A client keeps a local copy of the rows a user may see, plus an ordered **outbox** of local changes.
It talks to a server through two endpoints under a base URL `{url}`:

| Endpoint | Purpose |
|---|---|
| `POST {url}/pull` | Fetch rows changed since a cursor |
| `POST {url}/push` | Upload outbox mutations |

A sync cycle is: push until the outbox is empty, then pull until `hasMore` is false (D-23).

## 2. Transport

1. Requests and responses are JSON (`Content-Type: application/json; charset=utf-8`) over HTTPS.
   Servers MUST reject plain HTTP in production. Development servers MAY allow it on loopback.
2. Clients SHOULD send `Accept-Encoding: gzip` and MAY send gzip request bodies with
   `Content-Encoding: gzip`. Servers MUST accept both gzip and uncompressed request bodies and
   SHOULD gzip responses larger than 1 KB.
3. No other encodings (MessagePack, zstd, Protobuf) are part of v1 (D-08).

### 2.1 Request headers

Every request MUST carry:

| Header | Value |
|---|---|
| `Authorization` | `Bearer <token>` |
| `X-SyncFlow-Protocol` | `1` |
| `X-SyncFlow-Client` | Stable client id: a UUIDv7 generated once per install and database |
| `X-SyncFlow-Schema` | The client's schema `version` (integer) |

A server MUST answer `400 BAD_REQUEST` if a required header is missing or malformed, and
`400 PROTOCOL_UNSUPPORTED` if `X-SyncFlow-Protocol` is not a version it implements.

### 2.2 Error responses

Every non-200 response has a JSON body:

```json
{ "error": "RESET_REQUIRED", "message": "human-readable text" }
```

| Status | `error` | Client behaviour |
|---|---|---|
| 400 | `BAD_REQUEST`, `PROTOCOL_UNSUPPORTED` | Do not retry; surface as an error |
| 401 | `UNAUTHORIZED` | Refresh the token once and retry once; then pause sync. Never drop the outbox (D-24) |
| 403 | `FORBIDDEN` | Do not retry the request; surface as an error |
| 410 | `RESET_REQUIRED` | §6.3 |
| 413 | `PAYLOAD_TOO_LARGE` | Retry with a smaller batch |
| 426 | `UPGRADE_REQUIRED` | §8.2 |
| 429 | `RATE_LIMITED` | Retry after `Retry-After` |
| 5xx | any | Retry with backoff |

Per-mutation failures are not HTTP errors: they are results inside a `200` push response (§5).

## 3. Data model

### 3.1 Rows

- Every synced table has a primary key `id`: a UUIDv7 string generated by the client (D-10).
- Column names in JSON are the schema's column names. Types on the wire:

| Schema type | JSON |
|---|---|
| `t.id()`, `t.text()`, `t.ref()` | string |
| `t.int()` | number (integer, within ±2^53) |
| `t.real()` | number |
| `t.bool()` | `true` / `false` |
| `t.date()` | number: milliseconds since the Unix epoch, UTC |
| `t.json()` | any JSON value |
| optional column with no value | `null` |

- Each row in a response carries `_v`: an integer version that the server increments on every change
  to that row. Clients MUST NOT send `_v` inside a `patch`.
- Server-internal columns (`_seq`, `_xid`, `_deleted`) MUST NOT appear in responses.

### 3.2 Mutations

```jsonc
{
  "id": "0193d1e2-…",        // UUIDv7, unique per mutation, generated by the client
  "table": "todos",
  "op": "insert",             // "insert" | "update" | "delete"
  "rowId": "0193d1e1-…",
  "patch": { "title": "Milk" },   // insert: all set columns; update: changed columns only; delete: omitted
  "baseVersion": 6            // the row's _v the client last saw; null for inserts
}
```

## 4. Pull

### 4.1 Request

```json
{ "cursor": null, "limit": 1000 }
```

- `cursor` is the opaque string from the previous pull or push response, or `null` for an initial sync.
- `limit` is the maximum number of row changes (changes plus deletes) in the response. Servers MAY
  return fewer and MUST cap it at a server maximum (default 5000).

### 4.2 Response

```jsonc
{
  "changes": { "todos": [ { "id": "0193…", "title": "Milk", "done": false, "_v": 7 } ] },
  "deletes": { "todos": ["0193…"] },
  "cursor": "opaque",
  "hasMore": true
}
```

Rules:

1. The server MUST return only rows the authenticated user may read (`scope`), filtered on the server.
   It MUST NOT trust any filter sent by the client.
2. The server MUST return only tables and columns that exist in the client's schema version (§8).
3. A row MUST NOT appear in both `changes` and `deletes` of one response. Each row appears at most once,
   with its latest state.
4. The client MUST apply a page and store its `cursor` in one local transaction (D-23). It keeps pulling
   while `hasMore` is true.
5. Clients MUST treat `cursor` as opaque. Servers MAY change its format between releases.
6. Paging from `null` and incremental pulls are the same code path, so an interrupted initial sync
   resumes from the last stored cursor.

## 5. Push

### 5.1 Request

```json
{ "mutations": [ { "id": "…", "table": "todos", "op": "update", "rowId": "…", "patch": { "done": true }, "baseVersion": 6 } ] }
```

- At most 100 mutations per request; servers MUST answer `413 PAYLOAD_TOO_LARGE` above that.
- Mutations are in outbox order. Mutations for the same `rowId` MUST stay in their original order.

### 5.2 Response

```jsonc
{
  "results": [
    { "id": "…", "status": "applied", "row": { "id": "…", "done": true, "_v": 7 } },
    { "id": "…", "status": "duplicate", "row": { "…": "…" } },
    { "id": "…", "status": "rejected", "code": "EMPTY_TITLE", "row": null },
    { "id": "…", "status": "conflict", "row": { "…": "…" } }
  ],
  "cursor": "opaque"
}
```

1. `results` has exactly one entry per mutation, in request order, matched by `id`.
2. `status`:

| Status | Meaning | `row` |
|---|---|---|
| `applied` | Applied now | The row after the change (`null` for a delete) |
| `duplicate` | Already applied earlier (§5.3) | The stored result's row |
| `rejected` | Not applied: business rule, scope or validation | Current server row, or `null` if none |
| `conflict` | Not applied: stale `baseVersion` on a `version` table (§7) | Current server row |

3. `rejected` results carry `code`: an upper-snake-case string. Reserved codes:
   `ROW_DELETED`, `FORBIDDEN`, `INVALID_PATCH`, `UNKNOWN_TABLE`, `UNKNOWN_COLUMN`. Apps define their own
   codes in `validate` hooks or webhooks.
4. Each mutation is applied in its own server transaction, together with its idempotency record (§5.3).
   A failed mutation MUST NOT roll back other mutations in the same request.
5. `cursor` is a **write checkpoint**: a pull from this cursor onward reflects every mutation in this
   request. The client keeps rows marked pending until its pulled cursor has reached it (D-23).
6. `op: "insert"` for a `rowId` that already exists is applied as an update (upsert), so a retried insert
   is safe.
7. A mutation to a row outside the user's `scope` is `rejected` with `FORBIDDEN`. The server MUST check
   scope on the row before **and** after the change, so a client cannot move a row out of or into
   another user's scope.

### 5.3 Idempotency (MUST)

1. The server stores `sync_mutations(id PRIMARY KEY, user_id, applied_at, status, result_json)` and writes
   it in the same transaction as the mutation (D-11).
2. Before applying a mutation, the server looks up its `id`. If found, it MUST NOT apply it again and
   MUST return the stored result with `status: "duplicate"`.
3. A found `id` belonging to a different `user_id` MUST be `rejected` with `FORBIDDEN`.
4. Records are kept at least 30 days (configurable), and MUST be kept longer than the client's maximum
   outbox age (default 30 days).
5. Only `applied` results are stored; `rejected` and `conflict` are not, so a client may correct and resend.

## 6. Change tracking and deletes

### 6.1 Change sequence (MUST)

1. Every synced server row has `_seq` (64-bit integer), set by a database trigger on every insert,
   update and soft delete, so writes from any source (admin tools, scripts) sync too (D-12).
2. A pull returns rows with `_seq` greater than the cursor's sequence.
3. Servers MUST NOT use client clocks or `updated_at` timestamps to decide what changed.
4. **No skipped rows:** a pull MUST NOT advance the cursor past a row whose transaction might still
   commit with a lower `_seq`. On Postgres the trigger stores `_xid = pg_current_xact_id()` and a pull
   returns only rows with `_xid < pg_snapshot_xmin(pg_current_snapshot())`. Databases without that
   feature take `_seq` from a counter row updated inside the writing transaction.

### 6.2 Soft deletes and tombstones

1. Deleting a synced row sets `_deleted = true` and advances `_seq`. Pulls report it under `deletes`.
2. Servers purge tombstones older than `tombstoneDays` (default 90).

### 6.3 Reset

1. If a cursor is older than the tombstone purge horizon, or the server can't honour it, the server
   answers `410 RESET_REQUIRED`.
2. The client then deletes all synced rows, **keeps its outbox**, and pulls from `cursor: null`. Pending
   local changes are re-applied on top as usual (§7.3).

## 7. Conflicts

### 7.1 `merge` tables (default)

The server applies only the fields in `patch` onto the current row and increments `_v`. Edits to
different fields both survive; for the same field, the last mutation to reach the server wins.
`baseVersion` is informational.

### 7.2 `version` tables

If `baseVersion` differs from the row's current `_v`, the server MUST return `conflict` with the current
row and MUST NOT apply the mutation. The client resolves it with `onConflict` (M4-01).

### 7.3 Rules for every table

1. Delete wins: an `update` to a deleted row is `rejected` with `ROW_DELETED`.
2. On `rejected`, the client restores the returned server row (or removes the row if `row` is `null`),
   then re-applies its later pending mutations for that row.
3. On pull, rows with pending local mutations are rebased: the client writes the server row, then
   re-applies the pending patches on top.

## 8. Schema versions

1. The client sends its schema `version` in `X-SyncFlow-Schema`.
2. If it is below the server's `minSchemaVersion`, the server answers `426 UPGRADE_REQUIRED` and the app
   shows an update prompt.
3. The server returns only the tables and columns that exist in the client's version. A patch naming a
   column that doesn't exist in the client's version is `rejected` with `UNKNOWN_COLUMN`, never ignored
   silently.
4. Additive changes (new table, column or index) do not change `version`. Destructive changes (rename,
   removal, type change) increment it.

## 9. Realtime poke (optional)

Servers MAY offer `GET {url}/events` as Server-Sent Events. Events carry no row data (D-19):

```
event: poke
data: {}
```

On a poke, the client runs a normal sync cycle. Clients MUST work correctly without this endpoint.

## 10. Security requirements

1. TLS for every request (§2).
2. Authorisation (`scope`) on every pull and every mutation, checked on the server (§4.2, §5.2).
3. Servers MUST NOT log row data or tokens in production logs.
4. Mutation ids are not secrets; idempotency records are scoped by user (§5.3).
